# Runtime Engine

The runtime engine is the core of Exepad — it takes a `WebAppProps` JSON configuration generated by the AI builder agent and renders it as a live, interactive React application. This document explains how the rendering pipeline works, from configuration loading through component resolution, variable substitution, and styling.

**Key source:** `apps/runtime/client/src/`

---

## Pipeline Overview

```
WebAppProps config
    │
    ▼
ConfigService (loads, caches, validates)
    │
    ▼
Zustand Stores
├── appStore (config metadata, theme)
└── appStateStore (state)
    │
    ▼
PageRenderer (iterates page.components[])
    │
    ▼
DynamicRenderer (per component)
├── 1. State Key Extraction → scan props for $variable references (extractStateKeys)
├── 2. Conditional Rendering → evaluate showWhen expression (shouldRenderComponent)
├── 3. Variable Substitution → replace $variables with state values (resolveComponentProps)
├── 4. Component Loading → lazy-load from registry with sync cache fallback
└── 5. Render → wrap in ErrorBoundary, pass processed props to React component
```

## DynamicRenderer

The `DynamicRenderer` is the heart of the runtime. For every component in the configuration, it:

**Source:** `apps/runtime/client/src/components/DynamicRenderer.tsx`

### 1. Component Resolution

Each component in the config has a `componentType` string. The renderer resolves this to an actual React component via a **component registry**. In the current Code Focus architecture the registry holds exactly one entry, `"CodeComponentProps"` — mapped to the Code Component runtime that loads and renders AI-generated TSX. Any other `componentType` is unregistered: the lookup returns `null` and the renderer shows the `ComponentFallback` ("Component not found") box.

- `getComponentSync(type)` — Returns cached component immediately (no flicker)
- `getComponent(type)` — Async lazy-load with fallback
- Components are lazy-loaded on first use, then cached for subsequent renders

### 2. State Key Extraction

Before rendering, the renderer scans all component props for `$variable` references using `extractStateKeys()`:

```typescript
// Input: { "text": "Total: $count items, $totalPrice" }
// Output: Set { "count", "totalPrice" }
```

This extracts every `$variableName` pattern (excluding reserved words like `$payload`, `$event`, `$item`, `$index`).

### 3. Granular Zustand Selector

The extracted state keys are used to create a **granular Zustand selector** via `useShallow`. This means:

- A component referencing `$count` only re-renders when `count` changes
- A component with no `$variable` references never re-renders from state changes
- The selector subscribes to `_state` for the referenced keys

This is critical for performance — without it, every state change would re-render every component on the page.

### 4. Conditional Rendering

The `shouldRenderComponent()` function evaluates the `showWhen` prop (falling back to `visibilityCondition`):

```json
{ "componentType": "CodeComponentProps", "name": "WelcomeBanner", "modulePath": "/components/WelcomeBanner.tsx", "showWhen": true }
```

- `undefined` → always render
- `true`/`false` → boolean check

Only boolean values are supported. Code components handle their own visibility logic in JSX.

### 5. Variable Substitution

`resolveComponentProps()` walks the entire props tree and replaces `$variable` references with their current values from state:

```json
// Config:
{ "text": "You have $itemCount items totaling $totalPrice" }

// Resolved (with state: { itemCount: 5, totalPrice: 149.99 }):
{ "text": "You have 5 items totaling 149.99" }
```

### 6. Style Processing

Code Focus components receive compiled Tailwind CSS via the `CodeFocusCssLoader`, which loads pre-compiled stylesheets scoped under `@layer exepad-app`. The `classes` prop on JSON-configured components passes Tailwind utility classes directly.

### 7. Error Boundaries

Each component is wrapped in a `ComponentErrorBoundary` that catches render errors and shows a fallback UI instead of crashing the entire page.

### Edit Mode

In edit mode (for live configuration editing), the DynamicRenderer also:
- Subscribes to component update events via `ConfigUpdateContext`
- Supports hot reload — component data can be updated without a full page refresh
- Wraps editable components (Text, Heading) with `ComponentWrapper` for inline editing

## Component Registry

The component registry maps `componentType` strings to React components. It uses a lazy-loading pattern with synchronous cache fallback.

### How the AI Builder Agent Uses ComponentTypes

The AI builder agent generates Code Focus components — each page's `content` array contains `CodeComponentProps` entries that reference a TSX module:

```json
{ "componentType": "CodeComponentProps", "name": "DashboardOverview", "modulePath": "/components/DashboardOverview.tsx" }
```

`CodeComponentProps` is the only registered type — the legacy JSON-component and blog-page types (`ButtonProps`, `TextProps`, `BlogMainPage`, `BlogPostPage`, …) were removed along with the JSON-component system. See [Component Catalog](04-component-catalog.md) for details.

### Loading Strategy

1. **First render**: Check sync cache → if hit, render immediately (no loading state)
2. **Cache miss**: Show loading skeleton → async import → cache → render
3. **Subsequent renders**: Always sync from cache

## State Management

**Source:** `apps/runtime/client/src/stores/appStateStore.ts`

The runtime uses a Zustand store for shared state across code components. `frontend.logic.state` defines initial values with optional `$persist` support for localStorage persistence.

Code components access state via SDK hooks:
- `useAppState(key, initial)` — single value with setter
- `useArrayState(key)` — array with push/remove/updateItem/clear helpers
- `useApp(selector?)` — flat snapshot of all state with `setState`

All logic (derived values, data fetching, side effects) is handled directly in code components via SDK hooks (`useModel`, `useHandler`, `navigate`, `toast`, `useCurrentUser`). There is no declarative action system, computed values engine, or expression parser.

---

## Page Rendering

Pages are defined as arrays of components in the configuration. The runtime:

1. Resolves the current route to a `PageProps` object
2. Applies the page layout (boxed, wide, narrow, full-width)
3. Renders header components (if defined)
4. Iterates `page.components[]` and passes each to `DynamicRenderer`
5. Renders footer components (if defined)
6. For sidebar layouts, renders sidebar components in a side panel

---

## Data Fetching

Code components fetch backend data via SDK hooks:

- `useModel(modelName, options)` — CRUD operations with auto-fetch, filtering, sorting, pagination
- `useHandler(handlerName, options)` — Custom handler execution with auto-fetch support

These hooks call the backend via the RPC API (`sys_list`, `sys_read`, or custom handler) and manage loading, error, and data states internally.
