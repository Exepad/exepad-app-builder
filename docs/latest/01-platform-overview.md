# Platform Overview

> **Shipped architecture.** Exepad ships as a **single self-hosted Node +
> Python container**: SQLite databases, filesystem storage, and in-process
> backend dispatch, with no external service dependency beyond the LLM API you
> choose. The root [`README.md`](../../README.md#architecture) and
> [`CLAUDE.md`](../../CLAUDE.md) are the shortest description of the shipped
> design; [Architecture](02-architecture.md) is the long one.

## What is Exepad?

Exepad is a **full-stack application platform** that renders dynamic web applications from JSON configuration. It is purpose-built to serve an **AI builder agent** — an LLM-powered workflow that takes a user's natural-language prompt and generates a complete `WebAppProps` configuration. The Exepad runtime then interprets that configuration and produces a fully interactive React application with an auto-CRUD backend, all served from one self-hosted container the operator runs on their own machine.

**Core concept:** User prompt → AI builder agent → JSON config → live full-stack web app.

The platform is **AI-first by design**. The configuration schema (`WebAppProps`) is structured for reliable LLM generation: consistent patterns, predictable types, minimal ambiguity, and strong defaults. The AI builder agent is the primary producer of configurations — it generates pages, component trees, state management, backend models, and custom handlers, all from a single conversation with the end user.

---

## Core Principles

| Principle | Description |
|-----------|-------------|
| **Single Configuration** | One JSON document (`WebAppProps`) defines the entire app — UI, state, backend, theme. No build step for the app developer. |
| **Declarative + Code** | Models, CRUD, state, and theming are declarative JSON. UI components are Code Focus TSX — generated by the AI agent, rendered in the light DOM with compiled Tailwind CSS. |
| **Progressive Complexity** | Simple apps stay simple. Complex apps have JavaScript escape hatches: custom handlers for the backend and a full SDK for code components. |
| **Auto-Docking** | The frontend automatically discovers and wires backend APIs. Define a model in the config, and the runtime knows how to call `sys_create`, `sys_list`, etc. without manual endpoint configuration. |
| **LLM-Friendly** | The schema is designed for reliable AI generation. Consistent patterns, predictable types, minimal ambiguity. |
| **Single Container, No Cloud** | Everything runs in one self-hosted container: the frontend SPA and API gateway (Hono on `@hono/node-server`), the backend (app-backend dispatched **in-process**), the database (SQLite via `better-sqlite3`), and storage (the local filesystem under `/data`). The only external dependency is the LLM API you choose. |

## How It Works

```
┌─────────────────────────────────────────────────────────────────┐
│                     JSON Configuration                          │
│  {                                                              │
│    uuid, alias, name, version,                                  │
│    frontend: { pages, theme, logic },                           │
│    backend:  { models, handlers },                              │
│    security: { ... }                                            │
│  }                                                              │
└───────────────────────────┬─────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│                      Exepad Runtime                             │
│                                                                 │
│  ┌──────────────────────┐    ┌────────────────────────────────┐ │
│  │  Presentation Layer  │    │     Backend Layer               │ │
│  │  • DynamicRenderer   │    │     • Auto-CRUD (models)       │ │
│  │  • Code Components   │    │     • Custom Handlers (JS)     │ │
│  │  • State Management  │    │     • Per-app SQLite Database  │ │
│  │  • SDK Hooks          │    │     • Owner-scoped Data        │ │
│  └──────────────────────┘    └────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│              Single self-hosted container                       │
│  Node runtime (Hono) + in-process app-backend + Python agent    │
│  SQLite databases + filesystem storage under /data              │
└─────────────────────────────────────────────────────────────────┘
```

1. **Define** your app as a JSON configuration (`WebAppProps`)
2. **The runtime** reads the config and dynamically renders pages, components, and state
3. **The backend** automatically provides CRUD endpoints for declared models
4. **Everything** runs in one container the operator hosts — no cloud accounts beyond the LLM API

## The Two-Tier Backend

The backend uses a 2-tier model that covers the full spectrum from simple data storage to complex business logic:

| Tier | Coverage | What It Does | Code Required |
|------|----------|--------------|---------------|
| **Tier 1: Models (Auto-CRUD)** | ~80% of use cases | Automatic CRUD endpoints for SQLite tables. Define columns, types, and policies in JSON — get create, read, list, update, delete operations for free. | None |
| **Tier 2: Handlers (JavaScript)** | ~20% of use cases | Custom JavaScript functions for aggregations, multi-table operations, external API calls, complex business logic. | Yes — handler functions |

This split means most apps need zero backend code. When they do need custom logic, handlers provide full database access through a structured `HandlerContext`.

## How the AI Builder Agent Works

The Exepad platform is served exclusively through an **AI builder agent** — an LLM-based workflow that acts as the interface between end users and the platform:

```
┌─────────────┐     ┌───────────────────────┐     ┌──────────────────┐
│  End User   │────▶│  AI Builder Agent      │────▶│  Exepad Runtime  │
│  (prompt)   │     │  (LLM workflow)        │     │  (renders app)   │
│             │◀────│  generates WebAppProps  │     │                  │
│  (live app) │     │  JSON configuration    │     │                  │
└─────────────┘     └───────────────────────┘     └──────────────────┘
```

1. **User describes their app** in natural language ("I need a CRM with contact management and deal tracking")
2. **AI builder agent** interprets the request and generates a complete `WebAppProps` configuration — pages, code components, state, backend models, theme
3. **Exepad runtime** receives the configuration and renders a fully functional application
4. **User iterates** by describing changes; the agent updates the configuration

The AI builder agent is the sole producer of application configurations. The platform's schema, component SDK, and backend API are all designed to be reliably generated by LLMs.

## Who Exepad Serves

| Role | Relationship to Exepad |
|------|------------------------|
| **AI Builder Agent** | The primary consumer of the platform. Generates `WebAppProps` configurations from user prompts. The schema is designed for reliable LLM generation with consistent patterns and predictable types. |
| **End Users** | Interact with the AI builder agent to describe their app requirements. They experience the generated application, not the platform internals. |
| **Platform Engineers** | Maintain and extend the Exepad runtime — improving the backend and extending the component SDK. |

## Why AI-First?

Traditional app-building platforms are designed for human developers — they have GUIs, drag-and-drop builders, and visual editors. Exepad takes a fundamentally different approach:

**The schema is the interface.** Instead of a visual builder, the `WebAppProps` JSON schema is the primary API surface. It is designed to be:
- **Predictable** — Consistent patterns across all component types and model definitions
- **Complete** — A single document defines everything; no ambient state or external configuration
- **Validatable** — JSON Schema (Ajv) validation catches errors before rendering
- **Iteratable** — The AI agent can read, modify, and regenerate any part of the configuration

**Code Focus is the UI layer.** The AI agent generates TSX code components that render in the light DOM with compiled Tailwind CSS scoped via `@layer exepad-app`. Components access shared state, backend data, and navigation through SDK hooks (`useApp`, `useAppState`, `useArrayState`). A 4-stage validation pipeline (syntax, semantic, CSS compilation, style coverage) ensures generated components are correct before deployment.

## Key Differentiators

**vs. Code Generation (v0, Bolt, etc.)**
- The app definition is JSON configuration, not a code repository — the runtime interprets it directly
- UI components are generated TSX, but the app structure, backend, and state remain declarative JSON
- Iterating is a config + component update, not a full code refactor

**vs. No-Code Platforms (Bubble, Retool)**
- AI-native — designed for LLM generation, not manual drag-and-drop
- Full Tailwind CSS control — pixel-level design customization
- Self-hosted in a single container you own — no vendor lock-in, no cloud accounts

**vs. Traditional Frameworks (React, Next.js)**
- Zero build step for applications — configuration is interpreted at runtime
- Auto-CRUD backend with per-user data isolation built in
- State management, routing, and theming handled declaratively
