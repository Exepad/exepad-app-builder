# Backend Handler Configuration Guide

This guide covers the handler code schema: imports, HandlerContext API, SQL rules, and handler patterns for Cloudflare Workers with D1 (SQLite).

---

## Imports — ONLY `@exepad/sdk`

The ONLY allowed import is:
```typescript
import { HandlerContext } from "@exepad/sdk";
```

NEVER import anything else. No npm packages. No model names. No table names.
Model/table names (e.g., "employees", "orders", "contacts") are SQL identifiers —
use them ONLY inside SQL strings passed to `ctx.db.prepare()`, NEVER as imports.

---

## HandlerContext — Full API

```typescript
interface HandlerContext {
  /** D1 Database — use parameterized SQL ONLY */
  db: D1Database;

  /** Execute multiple D1 statements atomically as a batch */
  batch: (statements: D1PreparedStatement[]) => Promise<D1Result[]>;

  /** Current authenticated user */
  user: { id: string; email: string; roles: string[] };

  /** Input parameters from handler_plan.inputs */
  params: Record<string, unknown>;

  /** Structured logger */
  log: {
    debug(msg: string, data?: Record<string, unknown>): void;
    info(msg: string, data?: Record<string, unknown>): void;
    warn(msg: string, data?: Record<string, unknown>): void;
    error(msg: string, data?: Record<string, unknown>): void;
  };

  /** App configuration */
  config: { appId: string; appAlias: string };

  /** Model configs keyed by model name — check ownerScope dynamically */
  models: Record<string, {
    name: string;
    ownerScope?: 'user' | 'shared';
    softDelete?: boolean;
    columns: Array<{ name: string; type: string; isPrimary?: boolean; isNullable?: boolean }>;
  }>;
}
```

Handlers receive ONLY the fields above (`db`, `batch`, `user`, `params`,
`log`, `config`, `models`). There is no `ctx.services` and no `ctx.settings`.
To persist user profile fields, preferences, business info, currency, etc.,
define your own backend model (e.g. a `user_profiles` table) and read/write
it with parameterized SQL against `ctx.db`, scoped by `owner_id` like any
other `user`-scoped model.

---

## Handler Rules

Parse your input to get:
- `handler_plan.inputs` — the expected parameters (available via `ctx.params`)
- `handler_plan.outputs` — the expected return fields. **Your handler's return object MUST contain exactly these field names with matching types.** For example, if outputs includes `"totalRevenue: number"`, your return statement must include a `totalRevenue` property. Do NOT rename, re-case (e.g., `total_revenue` instead of `totalRevenue`), or omit any declared output field.
- `handler_plan.auth_level` — who can call this handler
- `handler_plan.handler_type` — "read" or "write"
- `handler_plan.logic` — step-by-step handler logic in plain English
- `model_plans` — ALL backend models. Each has:
  - `name` — the SQL table name (use in SQL strings, NOT as an import)
  - `columns` — column definitions (name + type)
  - `owner_scope` — "user" (filter by owner_id) or "shared"
  The handler may query any or all models (JOINs, aggregations).

---

## SQL Rules (CRITICAL)

1. **ALWAYS use parameterized queries** — NEVER string interpolation
2. **INSERT must include**: `owner_id`, `created_at`, `updated_at` — but NEVER `id` (auto-generated by AUTOINCREMENT)
3. **owner_scope filtering** — Check EACH model's `owner_scope` from model_plans:
   - If `owner_scope` is `"shared"`: do NOT add `WHERE owner_id = ?`. All users see all rows.
   - If `owner_scope` is `"user"` (default): MUST add `WHERE owner_id = ?` to scope data per user.
   - When a handler queries multiple models, check EACH model's `owner_scope` independently.
4. Timestamps with `new Date().toISOString()`
5. `.all()` returns `{ results: T[] }` — access via `result.results`
6. `.first()` returns `T | null` directly — no `.results` wrapper
7. Use `.run()` for INSERT/UPDATE/DELETE
8. **Soft delete**: When querying models with `softDelete: true`, you MUST manually add `WHERE "deleted_at" IS NULL`. Unlike auto-CRUD, custom handlers do NOT auto-filter soft-deleted rows.
9. **Use exact column names** from each model's `columns` list — always snake_case
10. **NEVER manually set `id`** — it is `INTEGER PRIMARY KEY AUTOINCREMENT`, omit from INSERT
11. **Status/enum string literals MUST be lowercase** in SQL WHERE clauses (e.g., `'open'`, `'offered'`, `'pending'`, `'active'`). D1/SQLite is case-sensitive — `'Open'` will NOT match seed data or frontend values which always use lowercase. If the handler_plan.logic mentions a capitalized status like "Open" or "Offered", convert it to lowercase in your SQL.

## Handler Examples

### CRITICAL: Status values must be lowercase in SQL

Seed data and frontend components always use lowercase status values.
SQL comparisons in D1 are case-sensitive — mismatched case returns 0 results.

```typescript
// ❌ WRONG — title-case will never match lowercase seed data
await ctx.db.prepare("SELECT COUNT(*) FROM jobs WHERE status = 'Open'")
await ctx.db.prepare("SELECT * FROM applicants WHERE status = 'Offered'")

// ✅ CORRECT — always use lowercase status values
await ctx.db.prepare("SELECT COUNT(*) FROM jobs WHERE status = 'open'")
await ctx.db.prepare("SELECT * FROM applicants WHERE status = 'offered'")
```

### Write Handler (INSERT — id is auto-generated, never set manually)
```typescript
import { HandlerContext } from "@exepad/sdk";

async function handler(ctx: HandlerContext) {
  const now = new Date().toISOString();

  const result = await ctx.db.prepare(
    'INSERT INTO bookings (owner_id, service_id, date, customer_name, status, created_at, updated_at) VALUES (?, ?, ?, ?, ?, ?, ?)'
  ).bind(ctx.user.id, ctx.params.service_id, ctx.params.date, ctx.params.customer_name, 'pending', now, now).run();

  return { bookingId: result.meta.last_row_id, status: 'pending' };
}

export default handler;
```

### Read Handler (SELECT with owner filtering)
```typescript
import { HandlerContext } from "@exepad/sdk";

async function handler(ctx: HandlerContext) {
  const result = await ctx.db.prepare(
    'SELECT * FROM products WHERE owner_id = ? ORDER BY created_at DESC'
  ).bind(ctx.user.id).all();

  return { products: result.results };
}

export default handler;
```

### CRITICAL: Returning array data from queries

When returning arrays of rows (time series, lists, grouped data), **always return
`result.results` directly** — NEVER `.map()` to rename or reshape columns.
SQL column names are already snake_case and the frontend component uses those
exact names from the model schema. Renaming breaks the contract.

```typescript
// ✅ CORRECT — return raw results, column names are already correct
const result = await ctx.db.prepare(
  'SELECT date, SUM(followers) as followers FROM daily_metrics WHERE owner_id = ? GROUP BY date'
).bind(userId).all();
return { series: result.results };

// ❌ WRONG — .map() renames columns, frontend won't find them
const series = result.results.map(row => ({ x: row.date, y: row.followers }));
return { series };
```

If you need computed fields, use SQL aliases (`SELECT x AS better_name`) instead of
JavaScript `.map()`. This keeps column names in one place (the SQL query).

### CRITICAL: Chart data MUST be array-of-objects

The frontend uses Recharts which requires **array-of-objects** where each object has
named keys matching the `dataKey` props on `<Charts.XAxis>`, `<Charts.Area>`, etc.

```typescript
// ✅ CORRECT — array-of-objects (Recharts-compatible)
const result = await ctx.db.prepare(
  "SELECT strftime('%Y-%m-%d %H:00', created_at) as hour, COUNT(*) as count FROM calls GROUP BY hour ORDER BY hour"
).all();
return { chartData: result.results };
// → { chartData: [{hour: "2026-01-01 09:00", count: 5}, ...] }

// ❌ WRONG — separate label/value arrays (Recharts cannot use this)
return { chartData: { labels: hours, values: counts } };
```

### CRITICAL: Handler outputs must include ALL fields the frontend needs

If the `handler_plan.outputs` lists a field, you MUST return it. If the frontend
needs a field from a related table (e.g., agent `status`, `qa_score`), include it
in your SQL SELECT and return it. Do NOT omit fields assuming the frontend will
hardcode or derive them.

```typescript
// ✅ CORRECT — SELECT all fields the frontend will display
const result = await ctx.db.prepare(`
  SELECT a.id, a.full_name, a.department, a.status,
    COUNT(c.id) as total_calls,
    ROUND(AVG(c.csat_score), 1) as avg_csat
  FROM agents a LEFT JOIN calls c ON a.id = c.agent_id
  GROUP BY a.id ORDER BY avg_csat DESC LIMIT 5
`).all();
return { agents: result.results };

// ❌ WRONG — omits status, frontend hardcodes "Available"
// ❌ WRONG — returns avg_csat but frontend expects qa_score
```

### CRITICAL: Percentage outputs are decimals in [0, 1]

Any output declared `type: "percentage"` (or `"percent"` / `"ratio"`) MUST be
returned as a decimal in `[0, 1]`. The component layer multiplies by 100 and
appends `%` for display. Returning `100` to mean "100 %" produces a UI render
of `10000 %`, which the validator now rejects.

```typescript
// ✅ CORRECT — return decimal ratio
const growthRate = prevCount > 0 ? (totalMembers - prevCount) / prevCount : 0;
return { growthRate };  // 0.125 → renders as "12.5%"

// ❌ WRONG — pre-scaled percent
const growthRate = prevCount > 0 ? ((totalMembers - prevCount) / prevCount) * 100 : 0;
return { growthRate };  // 12.5 → renders as "1250.0%"
```

This rule applies regardless of the field name (`growthRate`, `conversion`,
`utilization`, `share`, …). Components rendering these values use
`{(value * 100).toFixed(1)}%`.

### Aggregation Handler (shared owner_scope — NO owner_id filter)
```typescript
import { HandlerContext } from "@exepad/sdk";

// When a model's owner_scope is "shared", do NOT filter by owner_id
async function handler(ctx: HandlerContext) {
  const employeeCount = await ctx.db.prepare(
    'SELECT COUNT(*) as count FROM employees'
  ).first();

  const departmentCount = await ctx.db.prepare(
    'SELECT COUNT(*) as count FROM departments'
  ).first();

  return {
    employeeCount: employeeCount?.count ?? 0,
    departmentCount: departmentCount?.count ?? 0,
  };
}

export default handler;
```

### Aggregation Handler (user owner_scope — with owner_id filter)
```typescript
import { HandlerContext } from "@exepad/sdk";

async function handler(ctx: HandlerContext) {
  const userId = ctx.user.id;

  const contactCount = await ctx.db.prepare(
    'SELECT COUNT(*) as count FROM contacts WHERE owner_id = ?'
  ).bind(userId).first();

  // Aggregation example. NOTE: `status` here MUST be a declared column on
  // `tasks`. Only GROUP BY / filter on columns that exist in the model's
  // columns[] — never copy this `status` pattern onto a table that has no
  // `status` column (derive from the columns that DO exist instead).
  const tasksByStatus = await ctx.db.prepare(
    'SELECT status, COUNT(*) as count FROM tasks WHERE owner_id = ? GROUP BY status'
  ).bind(userId).all();

  return {
    contactCount: contactCount?.count ?? 0,
    tasksByStatus: tasksByStatus.results,
  };
}

export default handler;
```

### Multi-entity JOIN
```typescript
import { HandlerContext } from "@exepad/sdk";

async function handler(ctx: HandlerContext) {
  const result = await ctx.db.prepare(
    'SELECT o.*, c.name as customer_name FROM orders o JOIN customers c ON o.customer_id = c.id WHERE o.owner_id = ? ORDER BY o.created_at DESC'
  ).bind(ctx.user.id).all();

  return { orders: result.results };
}

export default handler;
```

---

## Rules Summary

1. `export default` for the handler function — REQUIRED
2. Import ONLY `HandlerContext` from `@exepad/sdk` — no other imports
3. Use parameterized SQL with `?` and `.bind()` — NEVER string interpolation
4. Include try/catch for error handling
5. Table names go in SQL strings — NEVER import them
